# ג׳רבי — מנוע ההחלטה: שכבה מתמטית, זיכרון שאילתות ו־LLM כשותף

29.10.2026 · גרסה 1 · ממשיך את [מנוע הבנת הבקשה](gerbi-ai-request-engine-he.md)

**ההחלטה במשפט אחד:** השכבה המתמטית מחשבת ניקוד שקוף לכל הצעה ומדרגת; זיכרון השאילתות מוסיף תיקון קטן ומוגבל לפי מה שאנשים עם אותה בקשה בחרו בפועל; ה־LLM נקרא רק כשהחישוב לא מספיק — בקשה שהמנוע לא הבין, או תיקו אמיתי בין ההצעות המובילות — ותשובתו נכנסת כתוספת חסומה, אף פעם לא כעקיפה של אילוצים.

## 1. ארכיטקטורה

```
בקשה חופשית ──► [1] מנוע הבנה דטרמיניסטי ──► brief + כיסוי (coverage)
                      │ כיסוי < 0.6 או סתירה
                      ▼
                 [3] LLM מפענח שני (JSON בסכמה קשיחה, במטמון)
                      │
חיפוש Volero ──► [2] שכבה מתמטית: אילוצים קשיחים → תועלות → ניקוד S
                      │            + [4] תיקון זיכרון m·β
                      │ פער בין 1 ל־2 < ε
                      ▼
                 [3] LLM שובר שוויון (top-K מקוצר, במטמון) → בונוס γ
                      ▼
              דירוג סופי + הסבר + תגיות + 3 המלצות מגוונות
                      │ אירועי משתמש (פתיחה, השוואה, בדיקת מחיר, שמירה)
                      ▼
                 [4] זיכרון שאילתות (חתימה → סטטיסטיקה מוחלקת)
```

| שכבה | קוד | רץ איפה | עלות |
|---|---|---|---|
| 1. הבנה | `dist/brief-engine.mjs` | דפדפן + שרת | 0 |
| 2. ניקוד | `dist/scoring.mjs` | דפדפן | 0 |
| 3. LLM שותף | `backend/llm-partner.mjs` | שרת בלבד (מפתח לא יוצא לדפדפן) | טוקנים, רק כשנדרש |
| 4. זיכרון | `backend/query-memory.mjs` | שרת | אחסון בלבד |

## 2. השכבה המתמטית — ניקוד טיסות

### 2.1 אילוצים קשיחים

מסננים שהמשתמש בחר או שפוענחו מהבקשה (ישירה, שעות, מזוודה, חברה, שדה) מסננים לפני ניקוד. הניקוד אף פעם לא מחזיר הצעה שנפסלה.

### 2.2 תועלות (כל אחת בטווח 0..1)

עבור הצעה i ברשימה, כאשר p_min, T_min הם המינימום ברשימה (מחיר במטבע אחד בלבד):

| תכונה | נוסחה | פרמטר |
|---|---|---|
| מחיר | u_p = exp(−k_p · (p_i − p_min) / p_min) | k_p = 3 (יקר ב־33% → 0.37) |
| זמן בדרך | u_t = exp(−k_t · (T_i − T_min) / T_min) | k_t = 2 |
| החלפות | u_s = max(0, 1 − 0.35 · s_i) | s_i = מקסימום החלפות בכיוון |
| המתנה | u_l = 1 אם L ≤ 120 דק׳, אחרת exp(−(L − 120)/360); × 0.6 בלילה; × 0.7 במעבר שדה | L = ההמתנה הארוכה |
| שעות | u_h = ממוצע הכיוונים: 1 בחלון המבוקש, 0.3 מחוץ לו; בלי בקשה: 0.6 להמראה 00–05, 0.85 לנחיתה +1 | |
| כבודה | u_b: נדרשה מזוודה → כלולה 1, לא נמסר 0.5, בתשלום/בלי 0.2; לא נדרשה → 1 | „לא נמסר” לעולם לא 1 כשנדרש |
| חברה | u_c = 1 אם תואמת העדפה, 0.8 אחרת; בלי העדפה 1 | |
| שדה | u_a = 0.7 לשדה רחוק (BVA, BGY), אחרת 1 | |

### 2.3 משקלות לפי הבקשה

משקל בסיס: מחיר 0.35 · זמן 0.20 · החלפות 0.15 · המתנה 0.10 · שעות 0.10 · כבודה 0.05 · חברה 0.03 · שדה 0.02.

מכפילים לפי ה־brief (ואחר כך נרמול ל־Σw = 1):

| תנאי | מכפיל |
|---|---|
| „זול / משתלם” | מחיר × 1.6 |
| ילדים בהרכב | החלפות × 1.5, המתנה × 1.5, שעות × 1.3 |
| ביקשו ישירה | החלפות × 2 |
| ביקשו מזוודה | כבודה × 3 |
| ביקשו שעות | שעות × 2 |
| ביקשו חברה | חברה × 3 |

### 2.4 ניקוד סופי

```
S_i = Σ_k w_k · u_k(i)                          ∈ [0, 1]
S'_i = S_i + β · m_i + γ · 1[i = LLM pick]
β = 0.08 (זיכרון), γ = 0.05 (LLM), m_i ∈ (−1, 1)
```

β ו־γ קטנים מכוונים: הם מסדרים מחדש רק הצעות קרובות. הצעה זולה ב־30% לא תרד בגלל זיכרון או LLM.

### 2.5 הסבר, תגיות והמלצות

- **הסבר:** תרומה c_k = w_k · u_k; משווים לממוצע הרשימה ומציגים את שתי התרומות החיוביות הגדולות במילים: „זולה ב־12% מהממוצע”, „קצרה ב־1:20 שע׳”, „ישירה”, „מזוודה כלולה”.
- **תגיות:** „הזולה ביותר” (argmin מחיר), „הקצרה ביותר” (argmin זמן), „המומלצת” (argmax S′). הצעה שאינה נשלטת בחזית פארטו של (מחיר, זמן) מסומנת „תמורה טובה”.
- **3 המלצות מגוונות (MMR):** בחירה חמדנית של argmax [λ·S′_i − (1−λ)·max_j sim(i, j)], λ = 0.7, כאשר sim = 1 לאותה חברה ושעת המראה בהפרש ≤ 60 דק׳, אחרת 0. כך לא מוצגות שלוש גרסאות של אותה טיסה.
- **מיון „מומלצות”** הוא ברירת המחדל כשיש brief; „סדר הספק”, „הזולה” ו„הקצרה” נשארים זמינים.

## 3. זיכרון שאילתות זהות

### 3.1 חתימה

החתימה היא SHA-256 של brief קנוני, בשתי רמות:

| רמה | שדות | שימוש |
|---|---|---|
| עדינה (fine) | מוצא, יעד, סוג נסיעה, חודש היציאה, נוסעים (1 / 2 / 3–4 / 5+), ילדים כן/לא, לילות (1–3 / 4–7 / 8+), סגנונות ממוינים | „אותה בקשה” |
| גסה (coarse) | מוצא, יעד, חודש, ילדים כן/לא | גיבוי כשאין מספיק נתונים ברמה העדינה |

טקסט חופשי לא נשמר ולא נכנס לחתימה. החתימה מחושבת אחרי נרמול, ולכן „זוג, 5 לילות בפריז ביוני” ו„אני ואשתי חמישה לילות ביוני לפריז” נופלות לאותה חתימה.

### 3.2 פריטים ואירועים

- **פריט טיסה:** מפתח מסלול יציב = קודי חברה + מספרי טיסה + שעות המראה לכל מקטע (למשל `W46034@19:40|W46035@05:40`). מזהי הצעה של הספק משתנים בכל חיפוש, ולכן לא משמשים.
- **פריט יעד:** מזהה היעד בקטלוג.
- **משקלות אירועים:** הצגה 0 (נספרת במכנה), פתיחת פירוט 0.3, השוואה 0.5, שיתוף 1.5, בדיקת מחיר 1, שמירה 2, הסתרה −0.5.

### 3.3 החלקה ודעיכה

לכל פריט i תחת חתימה: a_i = סכום משקלות דועך, n_i = מספר הצגות דועך. חצי חיים H = 30 יום. בעדכון:

```
a ← a · 2^(−Δt/H) + w        n ← n · 2^(−Δt/H) + 1[הצגה]
```

שיעור מוחלק (Beta, כיווץ לממוצע החתימה r₀):

```
r_i = (a_i + α · r₀) / (n_i + α),   α = 5
m_i = tanh((r_i − r₀) / max(r₀, 0.05))
```

בלי נתונים m_i = 0. שילוב רמות: m = (n_fine · m_fine + κ · m_coarse) / (n_fine + κ), κ = 10. כך חתימה חדשה נשענת על הגסה עד שמצטברים נתונים.

### 3.4 מטמון זהות

שאילתה זהה (אותה חתימה עדינה ואותו קלט ל־LLM) מקבלת את תשובת ה־LLM מהמטמון ב־0 טוקנים: פענוח נשמר 30 יום, שבירת שוויון יום אחד (מחירים משתנים).

## 4. ה־LLM כשותף להחלטה

### 4.1 מתי נקרא (gating)

| משימה | תנאי | קלט | פלט |
|---|---|---|---|
| פענוח שני | כיסוי < 0.6, או מילים משמעותיות שלא פוענחו (≥ 3), או סתירה (יעד שנשלל ונבחר) | הטקסט (≤ 600 תווים) + ה־brief החלקי | אותם שדות כמו המנוע, JSON בסכמה קשיחה |
| שובר שוויון | S′₁ − S′₂ < ε = 0.03 בין 3 המובילות, יש brief | טבלת תכונות מקוצרת ל־K ≤ 5 + ה־brief הקנוני | אינדקס בחירה + סיבה בעברית ≤ 80 תווים |

**כיסוי** = משקל התווים שפוענחו לישויות חלקי משקל המילים המשמעותיות (בלי מילות קישור), בטווח 0..1.

### 4.2 גבולות ההשפעה

- פלט הפענוח ממלא רק שדות ריקים. ערך שהמנוע חילץ במפורש, או שלילה מפורשת, גוברים תמיד.
- כל ערך עובר את אותה ולידציה כמו קלט משתמש: קודי שדה מהרשימה, תאריכים תקינים, מספרים בטווח.
- שובר השוויון מוסיף γ בלבד ורק בתוך top-K. הצעה מחוץ ל־K או שנפסלה לא תיבחר.
- סירוב, timeout, JSON לא תקין או חריגה מתקציב מחזירים התנהגות דטרמיניסטית רגילה בלי הודעת שגיאה למשתמש.

### 4.3 חיסכון בטוקנים

1. **Gating** — הרוב המכריע של הבקשות לא מגיע ל־LLM. היעד: פחות מ־15% מהבקשות לפענוח, ופחות מ־10% מהחיפושים לשבירת שוויון.
2. **מטמון זהות** (3.4) — חזרה על בקשה זהה עולה 0.
3. **קלט קומפקטי** — טבלת תכונות מעוגלת (מחיר, דקות, החלפות, המתנה, שעות, כבודה) כ־~40 טוקנים להצעה; בלי payload של הספק.
4. **פלט קשיח וקצר** — structured outputs (`output_config.format`, json_schema) בלי טקסט חופשי; סיבה ≤ 80 תווים.
5. **מאמץ נמוך** — `output_config.effort: "low"`: משימות חילוץ ובחירה קצרות.
6. **הנחיית מערכת יציבה** — אותו טקסט בכל קריאה (בלי תאריכים או מזהים), כדי שמטמון ההנחיות יעבוד כשהקידומת ארוכה מספיק.
7. **תקציב** — `GERBI_LLM_DAILY_TOKENS` (ברירת מחדל 200,000 ליום למופע), מפסק אחרי 3 כשלים רצופים ל־10 דקות, timeout של 8 שניות לפענוח ו־6 לשבירת שוויון.

### 4.4 ספק ומודל

- Anthropic Messages API דרך ה־SDK הרשמי (`@anthropic-ai/sdk`), בצד השרת בלבד; המפתח ב־`ANTHROPIC_API_KEY`.
- מודל ברירת מחדל `claude-opus-5-5` ($4 / $20 למיליון טוקנים). אפשר להחליף דרך `GERBI_LLM_MODEL`, למשל `claude-haiku-5-5` ($0.10 / $0.50), החלטה עסקית.
- `fallbacks: "default"` מופעל, כך שסירוב נשלח למודל חלופי באותה קריאה.
- בלי מפתח, המנוע כולו עובד דטרמיניסטית; ה־LLM הוא שיפור, לא תלות.

**אומדן עלות לקריאה:** קלט ~900 טוקנים, פלט עד ~300, כלומר ~$0.01 ב־Opus 5.5 או ~$0.0003 ב־Haiku 5.5. ב־1,000 בקשות ביום ו־15% gating: ~$1.5 ליום ב־Opus 5.5, ופחות אחרי מטמון.

## 5. פרטיות

- ל־LLM נשלח הטקסט שהמשתמש כתב לג׳רבי, אחרי הסרת מספרי טלפון ומיילים. לא נשלחים מזהים, IP או היסטוריה.
- זיכרון השאילתות שומר סטטיסטיקה מצרפית לפי חתימה מגובבת בלבד: בלי טקסט, בלי מזהה משתמש, בלי IP.
- מדיניות הפרטיות באתר מעודכנת בהתאם.

## 6. אחסון

| סביבה | זיכרון ומטמון |
|---|---|
| מקומי | קבצי JSON ב־`data/` (לא במאגר) |
| Vercel | Upstash Redis דרך REST כש־`UPSTASH_REDIS_REST_URL` ו־`UPSTASH_REDIS_REST_TOKEN` מוגדרים; אחרת זיכרון בתהליך (נמחק בין הפעלות) |

כתיבה היא read-modify-write למסמך אחד לחתימה. אם שני עדכונים מגיעים יחד, האחרון גובר: אובדן אירוע בודד לא משנה סטטיסטיקה מוחלקת.

## 8. בדיקות קבלה

1. אותה בקשה פעמיים: הקריאה השנייה ל־LLM מוגשת מהמטמון (0 טוקנים).
2. הצעה שנפסלה במסנן לא מופיעה, גם אם ה־LLM או הזיכרון היו מעדיפים אותה.
3. הצעה זולה ב־30% עם זמן דומה נשארת מעל הצעה שה־LLM בחר.
4. ללא מפתח API: כל המסלולים עובדים, `partner.used = false`.
5. אירועי שמירה חוזרים על מסלול מסוים מעלים אותו מעל מתחרה בעל ניקוד בסיסי זהה, בתוך β.
6. דעיכה: אחרי 30 יום משקל האירועים נחצה.
7. בקשה עם טלפון או מייל: אלה לא מופיעים בקלט ל־LLM.
8. ה־LLM מחזיר JSON לא תקין, סירוב או timeout: התשובה הדטרמיניסטית מוצגת בלי שגיאה.
